# zfy 语言基准测试报告（第一轮基线 + 第二轮迭代 + 第三轮迭代 + 第四轮迭代）

日期：2026-10-03 ｜ 环境：Windows x64，MinGW g++ 16.2.0，rustc 1.98.1（-O2），
clang 18.1.8，Python 3.12.10，zfyc（OCaml 4.14 + LLVM IR → clang 链接，原名 zyfc）。
输入：1 万个整数（stdin）；每个实现运行 10 次取均值/方差。

## 0-2. 第四轮迭代结果（seq 临时 move 优化 + 声明免预分配，10 次均值）

| 实现 | 均值(s) | 峰值内存 | zfy 相对 rust |
|------|--------:|---------:|---------:|
| rust | 0.126 | 5.89MB | 1.00x |
| cpp  | 0.147 | 5.75MB | 1.17x |
| zfy  | **0.151** | **5.2MB** | **1.21x** |
| python | 1.572 | 18.8MB | 12.5x |

- zfy 总耗时 0.174s → **0.151s**；相对 rust 1.37x → **1.21x**（已与 cpp 的 1.17x 基本持平）。
- 逐任务（vs 最快）：T1 1.08x / T2 1.03x / T3 1.11x / T4 **1.02x** / T5 1.08x —— 全部进入 1.1x 区间。
- T4 从 1.27x → 1.02x（超过 cpp 的 1.10x）。

第四轮已落地（P1：深拷贝消除第一步）：
- **seq 临时 move 优化**（mir.ml move_seq_temp + MMoveSeq 指令）：声明/赋值的右值是本语句
  产生的 seq 临时（切片结果等）时，所有权直接转移给变量——释放目标旧值后 store 指针，
  免去整体克隆与临时释放。临时单语句生命周期保证安全（无循环回边引用问题）。
- **声明带初值免预分配**（SSeqCopyK 不再先 MSeqAlloc）：原先 `int array cp[n] = base` 先分配
  n 个元素再克隆覆盖（纯浪费）；现在槽位保持 null 初值，直接由拷贝/移动覆盖。
- 顺带修复 MCopy/MMoveSeq 释放 string 元素数组旧值时 free_elems 标志恒 0 的潜在泄漏。
- 20 个示例回归全 PASS。
- 剩余差距：T3 1.11x（output 逐行 flush 未优化）、T1/T5 ~1.08x（i128 srem 软件除法、
  深拷贝语义下传参克隆），均在测量噪声边缘。

## 0-3. 第五轮迭代结果（I/O 快速路径：stdin 批量缓冲 + stdout 大缓冲）

- **stdin 快速读取**（runtime.c in_getc）：自管 64KB 缓冲 + 整块 fread，
  替代逐字符 getchar()（每次走 stdio 锁与调度）。1 万整数输入的系统调用
  从 ~6 万次 getchar 降到 ~1 次 fread/64KB。
- **stdout 64KB 缓冲**（zfy_io_init constructor 调 setvbuf）：默认 4KB → 64KB，
  逐行输出场景减少 16 倍 flush。
- 效果：T3 1.11x → **1.07x**（反超 cpp 的 1.22x，成为次快实现）。
- 本轮总耗时受机器噪声影响较大（T5 波动 ±10%）：zfy ~0.155s，相对 rust ~1.16x，
  与 cpp（~1.16x）持平。多轮测量的稳定结论为 1.15~1.25x。
- 20 个示例回归全 PASS。

- zfy 总耗时 0.3688s → **0.174s**（再快 **2.1x**）；相对 rust 差距 2.95x → **1.37x**（相对 cpp 1.22x）。

第三轮已落地（P1：数组/列表元素访问内联化）：
- MSeqGet/MSeqSet（非 string、非扩长写入）不再走 zfy_seq_get/zfy_seq_set_w 运行时函数：
  内联边界检查（icmp ult，同时覆盖负下标）+ 直接 GEP load/store 元素位模式，
  消除逐元素函数调用与 i128 中转槽。失败路径调用新增 runtime 函数 zfy_bounds_fail（不返回）。
- string 元素读写与列表扩长写入仍走运行时（深拷贝/扩长语义不变）。
- 20 个示例回归全 PASS；bench 总耗时校验和一致。

## 6. 关键结论

1. zfy 当前综合性能约为 C++/Rust 的 1/3.5，是 Python 的 3.5 倍，内存最优，编译最快。
2. **最大瓶颈是 T5（占总耗时 85%）**：i128 运算 + LLVM IR 以 -O0 编译。
   driver.ml 的 clang 调用未传任何优化标志，而 IR 大量使用 alloca 槽，
   -O0 下无 mem2reg，每次访问都走内存。
3. 次要瓶颈 T4（1.33x）：深拷贝语义 + 切片/克隆的 malloc/memcpy。
4. T1/T2/T3 均在 1.0~1.3x，差距不大。

## 7. 优化路线图（按优先级）

### P0 一行级改动（预计 T5 3.2x → ~1.2x，总耗时 → ~1.3x）
- driver.ml 链接命令加 `-O2`（或 `-O1 -Xclang -disable-O0-optnone`）：
  LLVM mem2reg 消除 alloca 槽 + 常量折叠 + 循环优化。
  代价：编译时间约 +100~200ms，仍显著快于 g++/rustc。

### P1 编译器增强
- i128 除法/取模：优先用 u128 路径（__umodti3），常量模数可改乘法逆元；
  hash 场景可提示用户用 u64/weak PRNG。
- 深拷贝消除（borrow-check-lite）：对「赋值后源不再使用」的数组/列表做 move 优化，
  免除 memcpy；切片写穿透改 copy-on-write。
- 运行时：数组/列表增加容量字段复用（列表已有，数组克隆可延迟分配）。

### P2 语言设计决策（见 notes.md LIM-1~5，待项目负责人决策）
- and/or 短路求值（守护惯用法的硬需求）
- 顶层 const 常量
- i32/i64 混合运算自动宽化 + 字面量按上下文定宽
- 列表声明支持整体深拷贝初值
- `push(x)` 等列表惯用内建

### P3 功能补全（长期）
- struct/match、泛型、并发（线程/channel）、模块系统增强。
